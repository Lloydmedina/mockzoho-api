Zoho OAuth 2.0 & Token Lifecycle

How authentication works in the Zoho CRM REST API

Use arrow keys or space to navigate

What is OAuth 2.0?

  • Industry-standard protocol for secure, delegated access
  • Third-party apps access user data without seeing passwords
  • Users grant scoped permissions — apps get time-limited tokens
  • Zoho uses OAuth 2.0 across all its APIs (CRM, Mail, Books, etc.)

"OAuth 2.0 enables third-party applications to access resources without requiring the end user to repeatedly authenticate." — Zoho Documentation

Key Terms

TermDescription
Client ApplicationYour app that wants to access Zoho data
End UserThe Zoho account holder who grants permission
Authorization ServerZoho's accounts server (accounts.zoho.com)
Access TokenShort-lived credential (1 hour) used in API calls
Refresh TokenLong-lived credential used to get new access tokens
ScopesPermissions defining what data the token can access

Three Grant Types

Authorization Code

  • For web apps with a backend server
  • User grants permission via browser
  • Most common for user-facing apps
  • Returns access + refresh token

Refresh Token

  • Server-to-server renewal
  • No user interaction needed
  • Recommended for CRM integrations
  • Returns new access token only

Client Credentials

  • Machine-to-machine auth
  • No user context — app acts as itself
  • Requires soid (sub-org ID)
  • No refresh token returned

For server-to-server CRM integration, the refresh_token grant is the recommended flow.

Step 1: Request Authorization Code

Browser redirect to Zoho's authorization endpoint:

GET https://accounts.zoho.com/oauth/v2/auth
    ?client_id=1000.XXXXXXXX
    &response_type=code
    &redirect_uri=https://yourapp.com/callback
    &scope=ZohoCRM.modules.ALL
    &access_type=offline
    &prompt=consent

ParameterRequiredDescription
client_idYesFrom Zoho API Console
response_typeYesMust be code
redirect_uriYesMust match registered URI
scopeYese.g. ZohoCRM.modules.ALL
access_typeYesoffline = get refresh token
promptNoconsent = force consent screen

Step 2: User Grants Permission

Zoho shows a consent screen to the end user:


Your App Name
wants to access your Zoho account
✓ Access your CRM modules (Cases, Visits, Products)
✓ Read and write records
✓ Access organization settings

On Accept: redirect to redirect_uri?code=1000.XXXXXXXX&location=us&accounts-server=https://accounts.zoho.com
On Deny: redirect to redirect_uri?error=access_denied
Authorization code is valid for 2 minutes only.

Step 3: Exchange Code for Tokens

Server-side POST to Zoho's token endpoint:

POST https://accounts.zoho.com/oauth/v2/token

  grant_type=authorization_code
  &client_id=1000.XXXXXXXX
  &client_secret=XXXXXXXX
  &redirect_uri=https://yourapp.com/callback
  &code=1000.XXXXXXXX

Response:

{
  "access_token": "1000.abc123.def456",
  "refresh_token": "1000.xyz789.uvw012",
  "api_domain": "https://www.zohoapis.com",
  "token_type": "Bearer",
  "expires_in": 3600
}

Using the Access Token

Every API call must include the token in the Authorization header:

GET https://www.zohoapis.com/crm/v3/Cases?fields=Subject,Status
Authorization: Zoho-oauthtoken 1000.abc123.def456

Important: Zoho's OAuth response says token_type: Bearer, but the actual API header prefix must be Zoho-oauthtoken, not Bearer. This is a Zoho-specific quirk.

Refreshing the Access Token

When the access token expires, use the refresh token to get a new one:

POST https://accounts.zoho.com/oauth/v2/token

  grant_type=refresh_token
  &client_id=1000.XXXXXXXX
  &client_secret=XXXXXXXX
  &refresh_token=1000.xyz789.uvw012

Response (no new refresh token):

{
  "access_token": "1000.newABC.newDEF",
  "api_domain": "https://www.zohoapis.com",
  "token_type": "Bearer",
  "expires_in": 3600
}

The refresh token stays the same — only the access token is renewed.

Revoking Tokens

When access is no longer needed, revoke the refresh token:

POST https://accounts.zoho.com/oauth/v2/token/revoke
Authorization: Basic {base64(client_id:client_secret)}

token=1000.xyz789.uvw012
&token_type=refresh_token

Response:

{ "status": "success" }

Revoking a refresh token also invalidates all access tokens generated from it. This is a cascade effect.

OAuth Error Handling

Zoho returns errors as HTTP 200 with an error body (a quirk):

// HTTP 200 (not 400!)
{ "error": "invalid_client" }

ErrorCause
invalid_clientWrong client_id or client_secret
invalid_codeExpired/used auth code, or wrong refresh token
invalid_redirect_uriredirect_uri doesn't match registered URI
unsupported_grant_typeUnknown grant_type value
invalid_requestMissing required parameter (e.g. soid)

For API calls (not OAuth), errors use a different format: {"code": "INVALID_TOKEN", "details": {}, "message": "...", "status": "error"}

Summary

  • 3 grant types: authorization_code, refresh_token, client_credentials
  • 3 endpoints: /oauth/v2/auth, /oauth/v2/token, /oauth/v2/token/revoke
  • 3 token types: auth code (2 min), access token (1 hour), refresh token (indefinite)
  • Auth header: Zoho-oauthtoken {token} (not Bearer)
  • OAuth errors return HTTP 200 with {"error": "..."}
  • Refresh tokens don't expire — use them to renew access tokens indefinitely
  • Revoking a refresh token cascades to all derived access tokens
  • Use domain-specific accounts URLs (US, EU, IN, AU, JP, CA)

For server-to-server CRM integration: use refresh_token grant. Get the initial refresh token once via authorization_code flow, then renew access tokens automatically.
