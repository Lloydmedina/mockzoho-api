Zoho CRM Error Codes & Rate Limits

Understanding API error responses and rate limiting in the Zoho CRM REST API

Use arrow keys or space to navigate

Error Response Format

All CRM API errors use the same envelope:

{
  "code": "INVALID_TOKEN",
  "details": {},
  "message": "invalid oauth token",
  "status": "error"
}

FieldDescription
codeMachine-readable error code (e.g. INVALID_TOKEN)
messageHuman-readable description
detailsAdditional context (field name, given value, etc.)
statusAlways "error" for errors

OAuth endpoint quirk: POST /oauth/v2/token returns HTTP 200 with {"error": "invalid_client"} on credential failures — not the CRM error envelope above.

Error Codes — HTTP 401 (Authentication)

INVALID_TOKEN 401

Message: "invalid oauth token"

Trigger: Missing/bad Authorization header or expired token

OAUTH_SCOPE_MISMATCH 401

Message: "invalid oauth scope to access this URL"

Trigger: Token lacks required scope for the endpoint

AUTHENTICATION_FAILURE 401

Message: "authentication failed"

Trigger: Authentication failed (e.g. wrong domain URL)

Error Codes — HTTP 403 (Authorization)

NO_PERMISSION 403

Message: "no permission to read"

Trigger: User lacks permission for the resource

FEATURE_NOT_SUPPORTED 403

Message: "The feature is not supported for your edition"

Trigger: Feature not enabled for the account edition

INVALID_MODULE 400

Message: "the module name given seems to be invalid"

Trigger: Unknown module name in the URL path

Error Codes — HTTP 404 (Not Found)

RESOURCE_NOT_FOUND 404

Message: "the record does not exist"

Trigger: Single-record GET on a non-existent ID

INVALID_URL_PATTERN 404

Message: "Please check if the URL trying to access is a correct one"

Trigger: Bad URL or unknown related list name

MANDATORY_NOT_FOUND 400

Message: "required field not found"

Trigger: Missing required field on write

Error Codes — HTTP 400 (Validation)

INVALID_DATA 400

Message: "invalid data"

Trigger: Bad field value or data type mismatch

INVALID_QUERY_PARAM 400

Message: "one of the expected parameter is missing or invalid"

Trigger: Bad query parameter (e.g. per_page over max)

INVALID_QUERY 400

Message: "invalid query formed"

Trigger: Malformed COQL query

Error Codes — HTTP 400 (Validation cont.)

REQUIRED_PARAM_MISSING 400

Message: "required parameter is missing"

Trigger: Required parameter missing (e.g. fields on list)

DUPLICATE_DATA 400

Message: "duplicate data"

Trigger: Duplicate value on a unique field

LIMIT_EXCEEDED 400

Message: "maximum number of records allowed is exceeded"

Trigger: Bulk write > 100 records, or COQL > 50 fields

Error Codes — HTTP 400 (Request format)

PATTERN_NOT_MATCHED 400

Message: "Please check whether the input values are correct"

Trigger: Parameter value not in allowed set (e.g. sort_order)

INVALID_REQUEST_METHOD 400

Message: "The http request method type is not a valid one"

Trigger: Wrong HTTP method for a /crm/ endpoint

LICENSE_LIMIT_EXCEEDED 400

Message: "Request exceeds your license limit"

Trigger: License limit exceeded (injectable via /__mock__/faults)

Error Codes — HTTP 400 & 429 (Limits)

UNABLE_TO_PARSE_DATA_TYPE 400

Message: "either the request body or parameters is in wrong format"

Trigger: Non-numeric record ID where integer expected

API_LIMIT_EXCEEDED 429

Message: "number of allowed API calls exceeded"

Trigger: API credit exhaustion (injectable via /__mock__/faults)

TOO_MANY_REQUESTS 429

Message: "concurrency limit exceeded"

Trigger: Rate limit hit — credits exhausted for the window

Error Codes — HTTP 500 (Server)

INTERNAL_ERROR 500

Message: "internal server error"

Trigger: Unexpected server error (injectable via /__mock__/faults)


Catalog-only codes: LICENSE_LIMIT_EXCEEDED, FEATURE_NOT_SUPPORTED, API_LIMIT_EXCEEDED, and INTERNAL_ERROR have no natural trigger in this mock but can be injected via POST /__mock__/faults to test client retry/backoff paths.

Rate Limits — How It Works

Zoho CRM uses an API credit system to limit request volume:

Client makes
CRM API call
→
Credit counter
decrements by 1
↓Credits remaining > 0
Request succeeds
200/201/204
↓Credits exhausted
Request rejected
429 TOO_MANY_REQUESTS

Window resets after the configured duration, restoring all credits.

Rate Limits — Configuration

Real Zoho CRM allows 5000 credits per minute on Enterprise edition. This mock mirrors that default.

Rate Limits — Response Headers

Every /crm/ response includes these headers:

X-RATELIMIT-LIMIT: 5000
X-RATELIMIT-REMAINING: 4998
X-RATELIMIT-RESET: 1726310460

HeaderDescription
X-RATELIMIT-LIMITTotal credits in the window (e.g. 5000)
X-RATELIMIT-REMAININGCredits left before exhaustion
X-RATELIMIT-RESETUnix timestamp when the window resets

Clients should read X-RATELIMIT-REMAINING to implement proactive backoff before hitting the limit.

Rate Limits — The 429 Response

When credits are exhausted:

HTTP/1.1 429 Too Many Requests

X-RATELIMIT-LIMIT: 5000
X-RATELIMIT-REMAINING: 0
X-RATELIMIT-RESET: 1726310460
{
  "code": "TOO_MANY_REQUESTS",
  "details": {
    "limit": 5000,
    "window_seconds": 60
  },
  "message": "Many requests fired than the allowed limit for a minute. Please check the header X-RATELIMIT-RESET for the reset time",
  "status": "error"
}

Two Types of 429

TOO_MANY_REQUESTS

  • Triggered by the real credit counter
  • Automatic when credits hit 0
  • Message: "concurrency limit exceeded"
  • Test via POST /__mock__/ratelimit {"remaining": 0}

API_LIMIT_EXCEEDED

  • Triggered by fault injection only
  • Not auto-triggered by the counter
  • Message: "number of allowed API calls exceeded"
  • Test via POST /__mock__/faults {"error_code": "API_LIMIT_EXCEEDED"}

Both return HTTP 429, but the code field differs. Clients should handle both.

Rate Limits — Credit Window Lifecycle

Full window — 5000 credits
5000 remaining
Partially consumed — 3000 used
3000 used
2000 left
Exhausted — 0 credits → 429
0 remaining
Window resets — credits restored
5000 restored

Client Retry Strategy

Send request
↓
Check X-RATELIMIT-REMAINING
↓If 0 → got 429
Read X-RATELIMIT-RESET
↓Wait until reset time
Retry with exponential backoff

  • Read X-RATELIMIT-REMAINING on every response
  • If remaining is low, slow down proactively
  • On 429, wait until X-RATELIMIT-RESET timestamp
  • Use exponential backoff with jitter for 500 errors
  • For 401 INVALID_TOKEN, refresh the access token then retry

Fault Injection — Testing Error Paths

The mock lets you force any error code on demand:

# Force all CRM calls to return 500
curl -X POST http://localhost:8090/__mock__/faults \
  -H "Content-Type: application/json" \
  -d '{"error_code": "INTERNAL_ERROR"}'

# Fail 30% of requests with INVALID_TOKEN
curl -X POST http://localhost:8090/__mock__/faults \
  -H "Content-Type: application/json" \
  -d '{"error_code": "INVALID_TOKEN", "error_rate": 0.3}'

# Inject 500ms latency on Cases endpoints only
curl -X POST http://localhost:8090/__mock__/faults \
  -H "Content-Type: application/json" \
  -d '{"latency_ms": 500, "path_contains": "/Cases"}'

# Fail next 5 requests then recover
curl -X POST http://localhost:8090/__mock__/faults \
  -H "Content-Type: application/json" \
  -d '{"error_code": "INTERNAL_ERROR", "remaining_failures": 5}'

# Clear all faults
curl -X POST http://localhost:8090/__mock__/faults/clear

Summary

  • 22 error codes across 6 HTTP status codes (400, 401, 403, 404, 429, 500)
  • All errors use the same envelope: {"code", "details", "message", "status"}
  • OAuth errors are different: HTTP 200 with {"error": "..."}
  • Rate limit: 5000 credits per 60s window, 1 credit per CRM call
  • Every CRM response includes X-RATELIMIT-* headers
  • Two 429 codes: TOO_MANY_REQUESTS (auto) vs API_LIMIT_EXCEEDED (injected)
  • Use /__mock__/faults to inject any error code for testing
  • Use /__mock__/ratelimit to control credit state for testing
  • Clients should implement backoff using X-RATELIMIT-RESET

For production: read X-RATELIMIT-REMAINING on every response and back off proactively before hitting 429.
